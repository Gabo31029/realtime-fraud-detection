# ADR-0006: A single feature implementation for batch and streaming

| Status | Date |
|---|---|
| Accepted | 2026-10-05 |

## Context

If training features and inference features are computed by different implementations, they eventually diverge and
the model degrades without anything visibly failing. This problem is known as training-serving skew.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| A shared library with a pluggable state store | A single implementation. Parity can be checked with an automated test | Dataset generation is slower because it replays history event by event |
| SQL for batch and Python for streaming | Fast batch | Two implementations that tend to diverge |
| Managed feature store (SageMaker Feature Store, Feast) | Industry-standard solution | Oversized for the project and hides the logic the project aims to demonstrate |

## Decision

All feature logic lives in a single library with no direct access to external data. Window state is abstracted
behind a common interface with two implementations: in-memory for batch and Redis for streaming. The training dataset
is generated by replaying history in time order with that same library.

## Consequences

- An automated test in continuous integration compares features and scores from both paths on a sample of 1,000 transactions.
- The dataset and the model store the feature schema version they were built with; the consumer refuses to start if they do not match.
- Any new feature requested by the data science team is added to the library, not to a separate analysis.
